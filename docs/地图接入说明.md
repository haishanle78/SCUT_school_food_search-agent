## 1. 项目如何使用地图

地图在这个项目里只做两件事：

| 用途 | 输入 | 输出 |
|------|------|------|
| **① 查店** | 店名 / 品类（如「潮汕牛肉」） | 门店 POI：uid、坐标、地址、行政区、类型标签 |
| **② 算路** | 出发点（校区某个门）+ 门店坐标 | 实际耗时（分钟）、距离（米） |

用户提问 → 大模型决定调用哪个工具 → 工具向百度发起请求 → 结果回填 → 生成推荐卡片。
**耗时、距离、坐标这些数字一律由后端从百度响应写入，模型不参与计算，也不允许编造。**

> 补充：地图只在校内使用 Web 前端不直接调用百度 API，所有请求都在服务端发出，AK 不会出现在浏览器里。

## 3. 需要用到的接口（共 3 个，均属 Web 服务 API）

| # | 接口 | 名称 | 用途 | 调用时机 | 频次 |
|---|------|------|------|---------|------|
| 1 | `GET /place/v2/search` | 地点检索（Place API v2） | 店名/品类 → POI 列表（坐标、地址、uid、类型标签） | 用户问"附近有什么"或指名某家店 | 每次问答 1–3 次 |
| 2 | `GET /place/v2/detail` | 地点详情（Place API v2） | 按 uid 精确获取门店详情（兜底，防止按店名模糊匹配出错） | 低频，仅在 uid 不在本次检索结果中时 | 每次问答 0–1 次 |
| 3 | `GET /direction/v2/{walking\|riding\|driving}` |  Direction API v2（路线规划） | 出发点坐标 + 门店坐标 → 耗时、距离 | 每次给出一家店的推荐前核实 | 每家店 1 次（默认**只查步行**） |

**说明：**
- 只需要 **Web 服务 API**，不需要 JS API、全景图、导航 SDK、鹰眼轨迹、地理编码等其它服务。
- 请求统一携带 `output=json`，坐标系为百度默认的 **bd09ll**。
- 路线规划默认只查「步行」一种方式——用户明确要骑行/打车时才额外查，以节省额度。

## 4. 配额需求

**使用场景**：课程项目 + 答辩演示，日活几十人以内，峰值集中在中午/傍晚饭点。

**估算**（按 100 人次/日、人均 3 次问答）：

| 接口 | 预估日调用 | 希望配额 |
|------|-----------|---------|
| 地点检索 + 地点详情 | ≤ 500 次/日 | **1000 次/日** |
| 路线规划 | ≤ 300 次/日 | **1000 次/日** |

**程序已自带额度保护**，实际调用量会明显低于上面估算：

- 全局限速 **2 QPS**（跨会话共享，不并发冲击）
- 日配额记账并持久化，超限当天停止调用
- 相同请求 **10 分钟缓存**，重复提问不重复计费
- 同一请求并发时只发一次（single-flight，其它请求等结果）
- 权限异常/额度耗尽后**自动熔断 10 分钟**，并降级为"只用本地知识库"，不会持续重试

如果贵方对 QPS 或日配额有具体限制，请告知数值，我们按此下调配置参数即可（无需改代码）。

## 6. AK 迁移后我们如何验证

拿到 AK 后由我方执行，一次性补录 57 家门店的坐标，预计消耗 **60–120 次检索**（一次性，之后长期走缓存）：

```bash

# 2) 补全现有 57 家门店的坐标（先预演，不写盘）
python tools/enrich_coords.py --dry-run

# 3) 跑地图治理测试（13 项，全部离线、不消耗额度）
python tests/test_map_gateway.py

# 4) 启动服务，页面右上角状态应从「地图未配置」恢复正常
python web/server.py
```

补坐标的判定是**从严**的：店名必须完全一致或相互包含，且直线距离在 6 公里内才写入，否则留空并人工确认——宁可没有坐标，也不写一个错的。

## 8. 调用链路（便于排查问题）

```
用户提问
  └─ 大模型判断需要查店
      └─ search_poi()  ──→  GET /place/v2/search      返回 uid + 坐标 + 地址
          └─ 大模型选定某家店
              └─ verify_route(uid)  ──→  GET /direction/v2/walking   返回分钟/米
                  └─ 后端把耗时、距离写进推荐卡片（模型不得改写这些数字）
```

相关代码位置（供技术支持核对实现）：

- `tools/map_gateway.py` —— 统一网关：限流、缓存、重试、错误分类、熔断、额度记账
- `tools/route_planner.py` —— 三个接口的实际调用方（检索 / 详情 / 路线）
- `tools/enrich_coords.py` —— 数据维护脚本，按店名批量补坐标
- `config.py` —— 配额、QPS、超时、缓存时长等参数集中配置

## 9. 已知限制（供参考，非请求事项）

1. **非正式店名命中率低**：如「cloud 意面」「B记鱼粥」这类学生口语化叫法，检索可能查不到或查到同名异店，需要人工补充地标或直接录入坐标。
2. **连锁店可能命中分店**：如「大雄寿司」有多家分店，需按 uid 人工确认是哪一家。
3. **尚未使用 v3 路线接口**：目前为 v2；若贵方建议升级到 v3，我们可以配合改造（改动集中在 `route_planner.py` 的一处调用）。
