# 评价知识库（RAG 语料）

`reviews.jsonl`：一行一条评价（JSON Lines），UTF-8 无 BOM。当前 58 条，覆盖 57 家门店
（两篇小红书攻略的人工整理，每家 1 条）。空库时接口如实返回 0 条，不拿示例数据充数。

> ⚠️ 现状：每家只有 1 条，属**单人观点**，页面会标「样本 1 条（不足 3）」且不参与口碑排序。
> 想让评分真正代表学生口碑，需要问卷数据补到每店 ≥3 条。

## 为什么单独一个文件

门店库（`restaurants.json` / `canteen.json` / `delivery.json`）存**门店基本面**：名称、坐标、菜系、人均。
评价是**一对多的长文本**，一家店可能有几十条，塞进门店对象会让文件难维护，也没法按评价粒度打分。
所以拆成独立语料，用 `store` 字段与门店名关联。

## 字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 全局唯一，建议 `r0001` 递增 |
| `store` | 是 | 门店名，尽量与门店库的 `名称` 完全一致（带分店名） |
| `rating` | 是 | 1–5 分，整数或半星 |
| `text` | 是 | 评价正文，20–120 字，含具体细节（菜品/分量/等待时间） |
| `tags` | 否 | 标签数组，如 `["辣","量大","排队"]`，用于口碑要点聚合与筛选 |
| `meal` | 否 | 餐段：早餐/午餐/晚餐/夜宵 |
| `price` | 否 | 该次实际人均（元），可与门店均价互相校验 |
| `date` | 否 | 消费日期 `YYYY-MM-DD`，用于「最近评价」排序 |
| `source` | 是 | 数据来源：问卷 / 点评整理 / 小红书整理（原创数据证据） |

见 `data/examples/demo_reviews.jsonl`（演示语料，`KB_DEMO=1` 时才读取，正式推荐不使用）。

## 入库纪律

- 只收**可溯源**的评价：问卷、自己整理的点评/小红书内容，不写爬虫抓的原文；
- 一人一次消费只算一条；刷分或明显情绪化的极端评价单独标注或剔除；
- 同一家店少于 `KB_MIN_SAMPLES`（默认 3）条时只报样本数，不对外显示均值；
- 评价里的人身攻击、隐私信息（手机号、宿舍号）必须打码后再入库。
